# ПОС — Преподавательская Оценка Студентов

Домашнее задание №2 по КПО. Консольная программа на Go, в которой преподаватель может добавлять студентов и критерии, ставить и исправлять оценки, смотреть итоги и экспортировать их в CSV.

В проекте использованы DDD, архитектура Ports & Adapters и три паттерна GoF: Factory, Facade, Strategy. Нужен Go 1.22 или новее, сторонних библиотек нет.

## Запуск

Из папки проекта:

```powershell
go run ./cmd/pos
```

В программе есть меню:

```text
1. Список студентов       2. Добавить студента
3. Список критериев       4. Добавить критерий
5. Оценки студента        6. Поставить или изменить оценку
7. Удалить оценку         8. Итог студента
9. Итоги всех студентов  10. Экспорт в CSV
0. Выход
```

Студенты получают ID вида `S1`, критерии — `C1`. Балл не должен превышать максимум критерия. Если выставить оценку ещё раз по той же паре «студент — критерий», старая заменится. Удаление оценки — пункт 7.

Данные хранятся в `data/pos.json` и остаются после перезапуска. Другой путь можно указать так:

```powershell
go run ./cmd/pos -data another-folder/pos.json
```

При вводе чисел подходят и точка, и запятая (`0.5` или `0,5`). ID нужно вводить латинскими буквами в правильном регистре: `S1`, `C1`.

## Демонстрация

Чтобы быстро посмотреть работу программы:

```powershell
go run ./cmd/pos -demo -export demo-results.csv
```

В этом режиме создаются два студента, три критерия и пять оценок. Результат:

```text
Демо: созданы 2 студента, 3 критерия, выставлены 5 оценок.
Отсутствующая оценка по критерию даёт 0 за этот критерий.
Анна Иванова (S1): 92.00%
Борис Петров (S2): 50.00%
CSV экспортирован: demo-results.csv (строк: 2)
```

Для демонстрации используется `MemoryRepository`, поэтому основной JSON-файл не меняется. CSV содержит столбцы `student_id`, `student_name`, `final_percent`, кодировка UTF-8.

## Доменная модель (DDD)

В коде использованы понятия из задания — это наш **Ubiquitous Language**:

| Понятие | В коде | Что означает |
|---|---|---|
| Студент | `Student` | Человек, которого оценивают |
| Критерий | `Criterion` | Название, максимум и вес |
| Оценка | `Evaluation` | Балл студента по критерию |
| Балл | `Score` | Проверенное числовое значение |
| Курс | `Course` | Студенты, критерии и оценки вместе |
| Итог | `ScoreService` | Расчёт результата по текущим оценкам |

`Student` и `Criterion` — **Entity**: у них есть свои ID. Даже два студента с одинаковым именем будут разными сущностями. `Score` — **Value Object**: у него нет отдельного ID, важно само значение. `Evaluation` относится к конкретной паре студента и критерия.

**Корень агрегата — `Course`.** Через него добавляются студенты и критерии, выставляются и удаляются оценки. Я оставил один агрегат, потому что по заданию достаточно одного курса. Так проще следить за согласованностью данных.

Главные **инварианты**:

- Имя студента и название критерия не должны быть пустыми.
- Названия критериев не повторяются без учёта регистра.
- Максимальный балл и вес положительные; `NaN` и бесконечность не допускаются.
- Балл находится в пределах от 0 до максимума критерия.
- Оценка возможна только для существующего студента и критерия.
- Для одной пары «студент — критерий» хранится одна актуальная оценка.

Проверки находятся в домене, а не только в консоли. Даже при чтении JSON данные восстанавливаются через методы `Course`. Итог отдельно не сохраняется: его каждый раз считает доменный сервис `ScoreService`.

## Как считается итог

По умолчанию применяется `WeightedStrategy`: каждый критерий влияет на результат с учётом своего веса.

```text
Итог (%) = 100 * сумма(вес * балл / максимум) / сумма весов
```

Например, лабораторные 9/10 с весом 0.5, домашние задания 18/20 с весом 0.3 и активность 5/5 с весом 0.2 дают **92%**.

Сумма весов не обязана быть равна 1 — формула сама её учитывает. Если оценки по критерию нет, вклад этого критерия равен нулю. Если критериев вообще нет, программа возвращает ошибку.

Есть и `EqualStrategy`: все критерии считаются равными, независимо от веса. Её можно включить командой:

```powershell
go run ./cmd/pos -policy equal
```

## Архитектура: Ports & Adapters

Я выбрал Ports & Adapters, чтобы логика оценивания не зависела от консоли и файлов. Структура проекта:

```text
cmd/pos/                     запуск программы
internal/domain/             сущности, инварианты, фабрика, стратегии
internal/application/        Facade, сценарии и интерфейсы портов
internal/adapters/console/   меню и ввод
internal/adapters/storage/   JSON и хранилище в памяти
internal/adapters/exportcsv/ экспорт результатов
internal/bootstrap/          создание и соединение компонентов
internal/demo/               демонстрационный сценарий
```

Основное направление зависимостей: `adapters → application → domain`. Домен не импортирует консоль, JSON или CSV. В `application` объявлены порты `CourseRepository` и `ResultsExporter`, а адаптеры их реализуют. В `bootstrap` всё соединяется через конструкторы — это и есть наш простой **DI-контейнер**.

## Паттерны GoF

Используются три паттерна — по одному из каждой группы:

| Группа | Паттерн | Где и зачем |
|---|---|---|
| Порождающий | **Factory** | `EvaluationFactory.Create` создаёт оценку, проверив студента, критерий и балл |
| Структурный | **Facade** | `application.Facade` даёт консоли готовые действия без прямой работы с хранилищем и доменом |
| Поведенческий | **Strategy** | `ScoringStrategy` позволяет переключать расчёт между `WeightedStrategy` и `EqualStrategy` |

Factory не даёт создать некорректную оценку штатным способом. Facade собирает работу нескольких компонентов в понятные операции. Strategy позволяет менять правило подсчёта без переписывания `ScoreService`.

Дополнительные паттерны не добавлял: для такого объёма задания этих трёх достаточно.

## Что не реализовано

Программа рассчитана на один курс. Пересдачи, апелляции и авторизация не входят в это ДЗ. Студентов и критерии можно добавлять и просматривать; редактирование и удаление для них в ТЗ необязательны. Для оценок исправление и удаление есть.

JSON хранится в одном файле. Сохранение идёт через временный файл, а затем его замену. Одновременная запись из нескольких процессов не предусмотрена. CSV содержит итоговые проценты, а не историю оценок.
